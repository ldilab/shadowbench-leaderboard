# ShadowBench Leaderboard

A static leaderboard for **ShadowBench** — a Lean 4 full-autoformalization benchmark that scores
*semantic alignment* with **SA-PASS**, not just compilation
([arXiv:2608.29270](https://arxiv.org/abs/2608.29270)).

It shows two things side by side:

1. **Reported results** — the paper's Table 3 numbers (n=178 snapshot), for public models.
2. **Live submissions** — models submitted through this site and evaluated on the lift backend
   (dataset v1.2), scored with the same SA-PASS definition.

## Metrics

All three are recomputed **per task** from a run's analysis payload and averaged over the run
(`denominator = total tasks`). Definitions follow the paper (Table 3 caption, Def. 5/6):

| Metric | Meaning | Per-task rule |
| --- | --- | --- |
| **Compile rate** | Generated Lean compiles standalone | `standalone_compile_ok` |
| **SA-pass (Soft)** | When it compiles, average of forward & backward checker pass rates | `compile ? (fwd + bwd) / 2 : 0` |
| **SA-pass** | Compiles **and** every forward & backward checker passes | `compile && fwd == 100% && bwd == 100%` |

> **Why recompute instead of using the API summary?** The backend's `overall` /
> `hiddenCheckerScore` fields are **not compile-gated** — a run can report `overall = 75%` with
> `compileRate = 0%`. Those overstate semantic alignment. `assets/metrics.js` is the single source
> of truth and is used by both the browser and the sync job, so the two never diverge.

## Structure

```
index.html            Leaderboard (paper table + live community table)
submit.html           Submission form + live job tracking (waiting UI)
assets/
  config.js           API base, "leaderboard-" prefix, adapter + eval defaults
  metrics.js          SA-PASS computation (shared by browser and CI)
  ui.js               theme, formatting, local job tracking, rate-limit gate
  leaderboard.js      renders both tables, sorting, level/group filters
  submit.js           builds the submission, polls status, shows results
  styles.css          light/dark theme
data/
  paper_results.json  transcribed Table 3 (public models)
  community.json      generated by the sync job (do not edit by hand)
scripts/sync_leaderboard.mjs   pulls the backend dump, writes community.json
.github/workflows/sync-leaderboard.yml   runs the sync every 30 min
```

## Deploy

This is `shadowbench.github.io`, served by GitHub Pages from the repository root.

- Push to the default branch; enable Pages (Settings → Pages → *Deploy from branch* → root).
- The **Sync community leaderboard** Action needs write permission
  (Settings → Actions → General → Workflow permissions → *Read and write*). It commits
  `data/community.json` every 30 minutes and can be run on demand from the Actions tab.

Local preview (ES modules require a server, not `file://`):

```bash
python3 -m http.server 8199   # then open http://127.0.0.1:8199
node scripts/sync_leaderboard.mjs   # refresh community.json manually
```

## How submission works

The form collects a display name, org, an OpenAI-compatible **model endpoint**, a **model id**,
and two sampling settings (max tokens, temperature). No API key is collected: submissions target
key-less endpoints. The benchmark scope is fixed, not user-selectable: every submission runs the full
**178-problem** ShadowBench set (all areas, L1 to L3), configured by `PROBLEM_COUNT`,
`SUBMISSION_AREAS`, and `SUBMISSION_LEVELS` in `config.js`. No open/closed/agentic label is attached to
community entries. It builds a `submissionSpec` around the backend's generic adapter and `POST`s to
`/api/submissions` with the id prefixed **`leaderboard-`**. The page then polls
`/api/submissions/{id}`, shows queue position and a waiting UI, and on completion fetches
`/analysis`, computes the three metrics, and shows a result card. Jobs are tracked in
`localStorage`, so the tab can be closed and reopened.

`model_cmd` and the docker runtime are **fixed in `config.js`** and never taken from user input,
see the security note below.

## Testing a submission end to end

`scripts/test_submit.mjs` runs the whole community pipeline against an OpenAI-compatible endpoint
(such as OpenRouter) with a small, cheap run, then prints the three metrics. The API key is read from
the environment only, never from the form or the repo:

```bash
OPENROUTER_API_KEY=sk-or-... node scripts/test_submit.mjs
# overrides: MODEL=openai/gpt-4o-mini COUNT=3 ENDPOINT=https://openrouter.ai/api/v1 PASSWORD=... NAME=... ORG=...
```

It submits a `leaderboard-test-<random>` job, polls to completion, and reports Compile rate,
SA-pass (Soft), and SA-pass. `COUNT` defaults to 3 to keep it cheap. It creates a real job (backend
compute and OpenRouter credits), and after the next sync the entry appears on the community board.
Pass `PASSWORD=` to attach a delete key so you can remove it afterwards.

### From the local browser

Serve the site (`python3 -m http.server`) and open `submit.html`. Because the API allows any origin and
`API_BASE` is the real backend, the form, waiting UI, and result card all work from localhost against the
live backend. A **Local test mode** panel (API key + a small problem count) is revealed only when the page
is served from localhost, so you can drive the real UI end to end. It never appears on the deployed site,
and `submit.js` reads the key and the small count only when the host is local, so the deployed site never
sends a key and always runs the full 178.

The endpoint is called by the eval backend, not the browser, so it must be reachable from the backend. A
LiteLLM proxy on your laptop is not, so expose it with a tunnel (for example
`cloudflared tunnel --url http://localhost:4000`) and use the resulting https `…/v1` URL, or point the
endpoint straight at `https://openrouter.ai/api/v1`. `litellm.config.example.yaml` is a starting config;
copy it to `litellm.config.yaml`, which is git-ignored along with `.env` and other local secrets (see
`.gitignore`).

## Deleting a submission

Each submission sets a **delete password** on the form. Submit stores a PBKDF2 hash of it (with a
random salt) in a public `delk:<salt>:<hash>` tag. To delete, use "Delete a submission" on
`submit.html` (or the Delete button on a tracked job): the page fetches the submission's tags, verifies
the password against the stored hash, and calls `DELETE /api/admin/submissions/{id}`.

> This is a **courtesy gate, not access control.** The hash is public (in the tag), so a weak password
> can be brute-forced, and the `DELETE` route is open (see item 2 below), so a determined caller can
> delete any submission without a password. Real ownership requires backend auth (a per-submission
> delete token issued and checked server-side). Use a password you do not reuse.

**Display name.** The name entered on the form is shown verbatim in the leaderboard's Model column.
The submission id is derived from it as `leaderboard-<slug>-<random>`, where `<slug>` is the name
lowercased with non-alphanumeric characters replaced by hyphens and truncated to 48 characters, and
`<random>` is a 6-hex suffix that keeps the id unique. The sync job filters community runs by this
`leaderboard-` id prefix (and the `leaderboard` tag).

> **Verification status.** The read paths were validated end to end (metric math checked against
> the live API on real runs, the sync pipeline run for real, both pages rendered). The **write path
> was not exercised in development**: the POST body shape was confirmed against the API's validation
> (missing `name`/`org` gives 422) and the 780 reference submissions, but no job was created from the
> repo. Use `scripts/test_submit.mjs` with `COUNT=3` for a cheap first real submission to confirm the
> contract. The status enum (`completed`/`running`/…) is inferred from the analysis payloads.

# Review & operating considerations

This section is the "what else should I think about" review. The feature requests are implemented;
several of the items below are **backend** issues that this static frontend cannot fix on its own
and that matter a lot for running this as a *public* board.

## What is implemented

- ✅ Public-model numbers sourced from the paper (Table 3), separated by group and difficulty level.
- ✅ Submission via the lift API with a `leaderboard-` id prefix.
- ✅ Waiting UI: live status, queue position, elapsed time, then a computed result card.
- ✅ SA-pass, SA-pass (Soft), and Compile rate, recomputed from run analysis per the paper's
  compile-gated definition.
- ✅ Model endpoint + hyperparameters in the form.
- ⚠️ "1 submission / 10 min / IP" — implemented as a **client-side courtesy gate** only (see 1).

## Things to address

**1. IP rate-limiting can't be enforced by a static site.** GitHub Pages runs no server code, so the
10-minute gate lives in the visitor's `localStorage` and is trivially bypassed (incognito, another
browser, or a direct `curl` to the API). To enforce it for real, put a tiny proxy in front of
`POST /api/submissions` — a **Cloudflare Worker** with a KV/Durable-Object counter keyed on
`CF-Connecting-IP` is the smallest option — or add the limit to the backend. The frontend gate
should stay as UX, but it is not a control.

**2. The backend has no authentication and permissive CORS.** `Access-Control-Allow-Origin: *` with
`GET/POST/PATCH/PUT/DELETE` and no auth means **any** website can call every route from a visitor's
browser, including `DELETE /api/admin/submissions/{id}` and `PATCH …`. Lock down the admin routes
(auth + same-origin/allowlist CORS) before publicizing the board.

**3. Admin endpoints leak live secrets.** `GET /api/admin/submissions.json` is currently open and
returns each submission's `env`, including `VLLM_API_KEY` / `OPENAI_API_KEY` / `OPENROUTER_API_KEY`
in cleartext. **Rotate any key that has passed through the system now**, then: require auth on all
`/api/admin/*`, and **redact `env`/secrets from every public response** (the analysis and leaderboard
payloads too).

**4. `model_cmd` looks like it is executed server-side from client input.** At least one stored
submission set `model_cmd` to `python3 -c "exec(base64.b64decode(...))"`. If the backend runs a
client-supplied `model_cmd`, that is remote code execution on the eval host by anyone. The frontend
here never sends a custom `model_cmd` (it's fixed to the vetted adapter), but the backend should
**ignore client-supplied `model_cmd`/`runtime`** and only accept a constrained set of fields
(endpoint URL, model id, sampling params) mapped onto an allowlisted adapter.

**5. Do not collect API keys in the browser.** The form no longer has a key field: submissions target
key-less endpoints, so no secret passes through the (currently open) backend or its admin dumps. Keep
it this way. If a keyed endpoint is ever required, proxy the model call server-side or register the key
out-of-band rather than posting it from the browser.

**6. Anonymous submission is a compute-DoS vector.** A full run is ~30s × hundreds of tasks (hours),
with only a few shared workers. The 10-minute gate doesn't bound total load. Consider: a real queue
cap per identity, requiring sign-in or a token for submission, a per-day budget, and **gating public
visibility behind the existing `verified` flag** so anonymous runs don't auto-publish.

**7. The two tables are not directly comparable.** The paper is the **n=178** snapshot; live runs use
dataset **v1.2** (660 hidden-checker tasks, more areas/levels). The UI states this and never ranks
across the two. To make them comparable, pin submissions to the published task-id list (the
`ldilab/shadowbench` release / the manifest's list path) via the eval `requestedTaskIds`.

**8. The public leaderboard dump is ~128 MB.** Too large for the browser, which is why the sync job
fetches it in CI. A backend endpoint that filters by id prefix and returns *summary rows only* would
remove the need to move 128 MB every cycle and let the site show a global board without CI.

**9. Reproducibility & trust.** Store and display each run's `submissionSpec` (model, params, seed,
lean version, commit), show tokens/$ per task for cost-aware ranking (fields exist but are 0), and
keep the `verified`/`reproducible` flags meaningful. A clear "how we score" page and a
link to each run's analysis (already linked) help others trust the numbers.

**10. Moderation & housekeeping.** Public `name`/`org` are user input — escape on render (done) and
consider a profanity/spoofing check. De-duplicate re-submissions of the same model (keep best or
latest). Decide a data-retention and takedown policy, and a license note for displayed results.

## Note on the paper numbers

`data/paper_results.json` is transcribed from Table 3 of arXiv:2608.29270v2 (Average + L1/L2/L3).
If the camera-ready or a later revision changes any value, update that file — it is the only place
the public-model numbers live.
